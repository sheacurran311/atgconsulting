## Mandatory phase gate

One active product phase at a time, in order below. Each phase is an implementation assignment, not a planning assignment. Within the phase, split work into small independently verifiable requirements. Complete all feasible engineering, appropriate admin/client/public UI, security, data integrity, tests, documentation and acceptance evidence. Use existing architecture and actual source files; no placeholder UI, mock-only functionality presented as production, or new parallel system.

For every phase, before advancing:
1. Reconcile existing code against all applicable R3 acceptance criteria and the previous mandate. List exact remaining tasks with stable IDs in the canonical plan and phase ledger.
2. Implement, integrate and test each task; fix regressions. Commit logical batches with the phase/requirement IDs in commit messages.
3. For each task record exact source paths, routes, database changes, commit SHA, test commands/results, UI evidence, limitations and remaining dependencies.
4. Run focused tests and required build/typecheck. Run full API and applicable browser regression suites before phase close; use isolated database and fixture/provider mock tests as appropriate. Obtain green CI for the phase checkpoint, or record CI explicitly pending/unavailable and do not call it CI verified. Do not skip or remove tests to pass.
5. Update docs/COMMERCIAL_LAUNCH_MASTER_PLAN_V4.md, docs/ATG_IMPLEMENTATION_RECONCILIATION.md and docs/qa/ATG_R4_PHASE_EXECUTION_LEDGER.md with the actual completed and outstanding criteria. Update historical plan/HANDOFF pointers as necessary. Write a concise phase checkpoint with commit and evidence references. Record current phase and exact next task. No progress percentage based on files or commits.
6. Exit only when every in-scope product criterion is implemented and locally verified (with CI verification where available), or an owner explicitly authorizes a deferral. A failing test, missing UI, unimplemented requirement, generic time constraint or incomplete specification is not a phase pass. Never substitute documentation, a search filter, annotations or partial improvements for the requested end-to-end feature.
7. A genuinely external staging/provider/legal dependency can be recorded separately as BLOCKED_EXTERNAL with exact prerequisite, tested mock/manual fallback, and owner action. It does not prevent a product-phase pass only when all independent product implementation is verified and the dependency is strictly external. Do not mark staging/production verified. If a real blocker prevents any remaining phase engineering, record it and request a specific decision; do not silently waive the gate.
8. After passing the gate, immediately begin the next phase without waiting for another prompt. If a session must end, commit safe tested work, leave the phase OPEN with exact unfinished items and resume that same phase in the next session. Do not publish a final completion report merely because the session ended. A new agent must resume from the first unpassed phase, not restart or cherry-pick another subsystem.

A phase's green CI alone does not prove feature completeness; acceptance evidence is criterion-specific. Use statuses OPEN, IN_PROGRESS, IMPLEMENTED_UNVERIFIED, LOCALLY_VERIFIED, CI_VERIFIED, PRODUCT_GATE_PASSED, BLOCKED_EXTERNAL, OWNER_APPROVED_DEFERRED, STAGING_VERIFIED, PRODUCTION_VERIFIED. No automatic owner-approved deferrals. Independent coordination review checks the gate after each checkpoint; it does not require an agent to stop between phases.
